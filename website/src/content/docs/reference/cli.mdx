## `verikt guide`

Generate architecture context for AI coding agents. Reads your `verikt.yaml` and writes rules, dependency constraints, and anti-patterns into the files AI agents load before writing code. Full detail — targets, the on-demand references under `.verikt/references/`, the instruction budget — is on the [`verikt guide` page](/reference/guide/).

```bash
verikt guide [flags]
```

### Flags

| Flag | Description | Default |
|------|------------|---------|
| `--target` | Which agent's files to write (`all`, `claude`, `cursor`, `copilot`, `windsurf`, `agents`) | `all` |
| `--catalog-only` | Write only the capability catalog; no `verikt.yaml` required | `false` |

`all` writes for every agent the project already uses, or for all of them when none is detected.

| Target | Always-loaded file |
|--------|--------------------|
| `claude` | `.claude/rules/verikt-index.md` and `.claude/rules/verikt-<category>.md` |
| `cursor` | `.cursor/rules/verikt.mdc` (verikt's section is moved out of a legacy `.cursorrules`) |
| `copilot` | `.github/copilot-instructions.md` |
| `windsurf` | `.windsurfrules` |
| `agents` | `AGENTS.md` |

Every target also gets the on-demand references in `.verikt/references/`. Commit them with the rest.

### Examples

```bash
# Every agent the project uses
verikt guide

# Target Claude Code specifically
verikt guide --target claude

# AGENTS.md, read by Codex, Antigravity and other agents
verikt guide --target agents
```

<Aside type="tip">
Prevention beats correction. Feed your AI agent the architecture rules before it writes code, and it produces correct code from the first line.
</Aside>

## `verikt new`

Scaffold a new project.

```bash
verikt new [name] [flags]
```

### Flags

| Flag | Description | Default |
|------|------------|---------|
| `--name` | Project/service name | positional arg |
| `--arch` | Architecture pattern (`hexagonal`, `flat`) | `hexagonal` |
| `--cap` | Capabilities (comma-separated) | none |
| `--module` | Go module path | `example.com/<name>` |
| `--output-dir` | Output directory | `.` |
| `--no-wizard` | Disable interactive wizard | `false` |
| `--set` | Template variable (key=value), repeatable | none |
| `--language` | Project language | `go` |

### Version Detection and Features

By default, verikt runs `go env GOVERSION` to detect the installed Go version. The detected version is used to resolve **feature flags** from the provider's feature matrix — enabling modern stdlib APIs and language features in the generated code.

You can override the detected version with `--set GoVersion=X.XX`. This is useful in CI environments or when targeting a specific Go version different from the one installed locally.

```bash
# Use detected Go version (default)
verikt new my-service --language go --no-wizard

# Target a specific Go version
verikt new my-service --language go --set GoVersion=1.24 --no-wizard
```

See the [Feature Matrix](/reference/features/) for the full list of version-gated features.

### Examples

```bash
# Interactive wizard — guides you through every choice
verikt new my-service --language go

# Non-interactive with all options
verikt new my-service \
  --language go \
  --arch hexagonal \
  --cap platform,bootstrap,http-api,mysql,docker \
  --module github.com/myorg/my-service \
  --no-wizard

# Target Go 1.24 features explicitly
verikt new my-service --language go --set GoVersion=1.24 --no-wizard
```

## `verikt check`

Validate a project against its `verikt.yaml` rules.

```bash
verikt check [flags]
```

### Flags

| Flag | Description | Default |
|------|------------|---------|
| `--path` | Path to project | `.` |
| `-o, --output` | Output format (`terminal`, `json`, `markdown`) | `terminal` |
| `--diff <ref>` | Report only findings in files changed since the merge base of `<ref>` and `HEAD` | none |
| `--staged` | Report only findings in files in the git staging area | `false` |
| `--detectors` | Run only the built-in detectors | `false` |
| `--proxy-rules` | Run only proxy rules | `false` |
| `--rule <id>` | Run a single proxy rule | none |
| `--decisions` | Run only decision gate validation | `false` |
| `--allow-degraded` | If the analysis engine is unavailable, skip the built-in detectors with a warning instead of failing | `false` |

`--detectors`, `--proxy-rules`, `--rule` and `--decisions` each narrow the run to one kind of check, so they cannot be combined.

### Checking Only What Changed

`--diff main` compares against the merge base of `main` and `HEAD`, not against `main`'s current tip, so on a branch that has fallen behind it reports what the branch changed rather than everything `main` moved on. The comparison is with the working tree, so committed and uncommitted work are both included. A ref that git cannot resolve is an error, not an empty file list: an empty list would filter every finding away and report a pass. An empty ref, or one starting with `-`, is rejected before git sees it.

`--diff` and `--staged` include added, copied, modified and **renamed** files. Renames used to be left out, so every finding in a file the branch had moved — including one moved and then edited — disappeared from the report.

### When the Analysis Engine Is Unavailable

The built-in detectors (dependency rules, structure, function metrics, anti-patterns) run on the analysis engine embedded in the binary and extracted to a cache directory on first use. A cached engine is used only if it is a regular file, not a symlink, with the expected size, permissions and SHA-256; anything else is extracted again.

If the engine cannot be extracted — an unwritable cache directory, for example — `verikt check` fails, and the error names the cause. It does not quietly skip the detectors and report a pass. `--allow-degraded` opts into skipping them: a warning on stderr says the detectors did not run, and only proxy rules and decision gates are checked. stdout is untouched, so `-o json` stays parseable. `--allow-degraded` is refused together with `--detectors`, which would leave nothing to check. `--decisions`, `--proxy-rules` and `--rule` never need the engine.

### What It Does Not Analyse

**Test files (`_test.go`) are excluded from every check, including dependency
rules.** A test reaches across layers to assemble a fixture, so counting its
imports reports violations for code that is not part of the architecture. The
consequence is worth knowing before you design around it: an import that only
exists in a test will not be flagged.

**Generated files are excluded.** A file carrying Go's
`// Code generated ... DO NOT EDIT.` marker before its package clause is skipped
— regenerating it would restore any finding, so the finding is not actionable.

**Nested modules are excluded.** A directory with its own `go.mod` is a different
project; its packages belong to that module's import path. Point `--path` at it
to analyse it on its own.

### What It Checks

verikt runs **14 AST-based detectors**:

- **Dependency violations** — imports that cross component boundaries
- **Required directories** — components with missing directories
- **Forbidden directories** — directories that shouldn't exist
- **Function complexity** — functions exceeding line/param/return limits
- **Component coverage** — percentage of components with source files
- **Anti-patterns** — common architectural violations
- **Unapproved entrypoints** (`cmd_allowlist`, Go only, opt-in) — a `package main`
  in the project root or under `cmd/` that `check.allowed_entrypoints` does not
  list. Off unless that key is set; see the [`check` reference](/reference/verikt-yaml/#check)
- **Live agent configuration in fixtures** (`live_dot_claude_fixture`, always on)
  — a `.claude/` directory holding `skills`, `rules`, `hooks` or `settings.json`
  under a path segment named `test`, `tests`, `testdata`, `fixtures`, `evals` or
  `examples`

The second exists because a fixture an agent can find is not a fixture. Coding
agents load `.claude/` directories as instructions, so a test subject stored as a
live `.claude/` tree becomes the instructions of whoever works on the tests. Store
it as `dot-claude/` and copy it to `.claude/` inside `t.TempDir()` when the test
runs. A `.claude/` with none of those entries loads nothing and is not reported;
`.git`, `node_modules` and `vendor` are not searched, symlinks are not followed,
and `check.exclude` applies.

Both are reported under **STRUCTURE VIOLATIONS** and in the JSON `violations[]`
array, at warning severity, so neither fails the check unless you raise it with
`severity_overrides`. `live_dot_claude_fixture` names the directory; with
`--diff` it is kept when any file inside that directory changed.

### Exit Codes

| Code | Meaning |
|------|---------|
| 0 | No error-severity violations. Warnings may be present. |
| 1 | An error-severity violation was found, a proxy rule could not run, or the check itself failed: no `verikt.yaml`, an unknown capability in it, an unresolvable `--diff` ref, or the analysis engine unavailable without `--allow-degraded` |

Warnings never affect the exit code, so a finding you have chosen to live with
cannot block a pipeline. The exit code is the same in every output format —
`--output json` reports the same verdict it prints.

A proxy rule whose scope matches no files is reported as **stale** and fails the
check: a rule that did not run has not passed. A rule that ran and found nothing
is passing, not stale.

### Waiving a Finding

Any finding can be waived with `severity_overrides`, anti-patterns included. A
waiver requires a reason, so the justification lands in the diff where a reviewer
sees it:

```yaml
severity_overrides:
  god_package:
    - severity: ignore
      reason: "the shared domain vocabulary; 27 types + 15 constants, nothing to trim"
      paths: ["internal/core/**"]
```

Waived findings are still reported, in a `WAIVED` section and in the `waived[]`
array of the JSON output, and they do not affect the exit code. A finding that
disappeared entirely would be indistinguishable from one the detector never
found.

### JSON Output

`--output json` emits a `schema_version` field. Check it before parsing — key
names are stable within a version, not across them.

`violations[]`, `anti_patterns[]` and `waived[]` are always present and always
arrays, so they are safe to iterate on a passing project.

```json
{
  "schema_version": 2,
  "result": "fail",
  "violations": [
    { "severity": "error", "file": "domain/order.go", "rule": "dependency", "message": "..." }
  ],
  "anti_patterns": [
    { "severity": "error", "name": "sql_concatenation", "file": "repo/db.go", "message": "..." }
  ],
  "waived": [
    { "category": "anti_pattern", "rule": "god_package", "file": "internal/core", "reason": "..." }
  ]
}
```

To gate a pipeline, read `result`:

```bash
verikt check --output json > verikt.json
jq -e '.result == "pass"' verikt.json
```

`result` is the same verdict the exit code carries, so gating on either is
equivalent — and it accounts for every category. Selecting on severity across
`violations[]` and `anti_patterns[]` does **not**: those two arrays hold the
built-in detector findings only. An error-severity proxy-rule violation lives in
`proxy_rules.violations[]`, a rule that could not run appears only in
`proxy_rules.statuses[]`, and decision-gate failures are in
`decision_violations[]`. A gate built from the two top-level arrays passes on all
three.

To count findings by severity — for a debt report rather than a gate — include
every source:

```bash
jq '[(.violations // [])[], (.anti_patterns // [])[], (.proxy_rules.violations // [])[]]
    | group_by(.severity) | map({severity: .[0].severity, count: length})' verikt.json
```

### Example Output

```
verikt check

Architecture: hexagonal
Components: 4 defined

Dependency Violations: 0
Structure Issues: 0
Function Issues: 0

Component Coverage: 100% (4/4)
Compliance: 100%

✓ All checks passed
```

## `verikt add`

Add one or more capabilities to an existing project.

```bash
verikt add <capability> [capability...] [flags]
```

Capabilities are validated against the provider's templates, conflicts are checked, and transitive dependencies are auto-resolved. **Existing files are never overwritten** — only new files are created.

### Flags

| Flag | Description | Default |
|------|------------|---------|
| `--dry-run` | Show what would be added without writing any files | `false` |

`--dry-run` reports the files it would create and which capabilities it would
resolve, and leaves `verikt.yaml` and the generated guides untouched.

### What It Does

1. Finds `verikt.yaml` in the current directory
2. Validates that each capability exists and doesn't conflict
3. Auto-resolves transitive dependencies (e.g., `bff` pulls in `http-api`)
4. Renders only new capability files, skipping any that already exist on disk
5. Updates `verikt.yaml` with the new capabilities
6. Regenerates `verikt guide` output

### Examples

```bash
# Add a single capability
verikt add redis

# Add multiple capabilities at once
verikt add kafka-consumer observability

# Add a capability with transitive deps
verikt add bff  # auto-adds http-api if not present
```

### Example Output

```
Adding capabilities:
  + http-api (auto-dependency)
  + bff
  Created: adapter/httphandler/handler.go
  Created: adapter/httphandler/router.go
  Skipped (exists): config/config.go

Done: 5 files created, 1 files skipped, 2 capabilities added
Auto-resolved dependencies: http-api
```

## `verikt diff`

Show structural drift between `verikt.yaml` and files on disk. Like `terraform plan` for code architecture.

```bash
verikt diff [flags]
```

### Flags

| Flag | Description | Default |
|------|------------|---------|
| `--path` | Project path to diff | `.` |
| `-o, --output` | Output format (`terminal`, `json`, `markdown`) | `terminal` |

### What It Reports

For each capability declared in `verikt.yaml`, diff checks whether the expected files exist:

| Status | Meaning |
|--------|---------|
| `ok` | All expected files are present |
| `partial` | Some files present, some missing |
| `missing` | All expected files are missing |

The **drift score** (0.00 = perfect, 1.00 = completely drifted) tells you how far reality has diverged from the declared architecture.

### Examples

```bash
# Check drift in current project
verikt diff

# Check a specific project
verikt diff --path ./my-service

# Get JSON output for CI
verikt diff -o json
```

### Example Output

```
verikt Diff — hexagonal + 4 capabilities
═══════════════════════════════════════════════════════
  ✓ architecture       all files present
  ✓ http-api           all files present
  ✗ redis              2 missing files
    - adapter/redisrepo/connection.go
    - adapter/redisrepo/repository.go
  ✓ docker             all files present

═══════════════════════════════════════════════════════

Summary: 3/4 capabilities fully present | drift score: 0.12
```

<Aside type="tip">
Use `verikt diff -o json` in CI pipelines to fail builds when drift exceeds a threshold.
</Aside>

## `verikt init`

Initialize an `verikt.yaml` for an existing project.

```bash
verikt init [flags]
```

### Flags

| Flag | Description | Default |
|------|------------|---------|

| `--no-wizard` | Skip interactive wizard | `false` |

<Aside type="note">

## `verikt setup`

Register verikt globally with the AI agents installed on this machine. For Claude Code it also offers to install the verikt skills, which add `/verikt:init`. Neither Homebrew nor the install script runs it for you (the script does with `--setup`).

```bash
verikt setup [flags]
```

### Flags

| Flag | Description | Default |
|------|------------|---------|
| `--check` | Report status without writing; exit 1 if any agent is stale | `false` |
| `--force` | Rewrite even if the installed version matches | `false` |
| `--uninstall` | Remove verikt's global files | `false` |
| `--codex` | Also manage verikt's section in `~/.codex/AGENTS.md` | `false` |
| `--antigravity` | Also manage verikt's section in `~/.gemini/GEMINI.md` | `false` |

Claude Code, Cursor and Windsurf are configured automatically when their config directory exists (`~/.claude`, or `$CLAUDE_CONFIG_DIR` when set; `~/.cursor`; `~/.windsurf`). verikt writes its own `verikt.md` into that agent's `rules/` directory. It never creates an agent's config directory.

Codex and Antigravity keep their global instructions in one file you also edit, so they are opt-in. With `--codex` or `--antigravity`, verikt writes only the section between its `<!-- verikt:global:start -->` and `<!-- verikt:global:end -->` markers and leaves the rest of the file alone; malformed markers stop it rather than risk your content. The same flags select them for `--check` and `--uninstall`. Without the flag, an installed Codex or Antigravity is reported and left untouched.

<Aside type="caution">
The Codex and Antigravity file locations have not yet been checked against each vendor's current documentation ([#19](https://github.com/diktahq/verikt/issues/19)). If your agent reads its global instructions from somewhere else, the section verikt writes will not be loaded.
</Aside>
