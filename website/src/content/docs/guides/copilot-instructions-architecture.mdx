GitHub Copilot reads `.github/copilot-instructions.md` and includes it in every chat request. Most teams either don't know this file exists or fill it with vague guidelines like "follow best practices." It rarely contains the specific, structural rules that would make suggestions actually fit the codebase.

`verikt guide --target copilot` generates `.github/copilot-instructions.md` with your layer boundaries, dependency direction, installed capabilities, and interaction warnings — derived directly from `verikt.yaml`. Copilot gets your architecture on every request.

## Quick start

Install verikt, then generate the instructions file:

```bash
brew install diktahq/tap/verikt
verikt guide --target copilot
```

The generated content lands at `.github/copilot-instructions.md`. Copilot picks it up automatically on next session.

## What gets generated

The file contains your architecture context in a format Copilot can act on. For a layered service scaffolded with `grpc`, `postgres`, `circuit-breaker` and `migrations`, the layer and capability sections read:

```
## Layer Rules

- **handler**: depends on service, model, platform
- **service**: depends on repository, model
- **repository**: depends on model, platform
- **model**: depends on nothing (innermost)
- **platform** (optional: may be absent): depends on model
- **app**: depends on handler, service, repository, model, platform

## Active Capabilities

**grpc**, **postgres**, **circuit-breaker**, **migrations**. Wiring patterns and the full catalog: `.verikt/references/capabilities.md`.
```

The agent knows the exact constraint — `service` depends on `repository` and `model`, nothing else — not a vague principle. The file stays short because it is sent with every request; the directories for each layer, the forbidden imports (``- `service` NEVER imports from `handler` ``) and the capability wiring live in `.verikt/references/`, and the file tells Copilot when to read each one.

## Sentinel-based merging

If `.github/copilot-instructions.md` already exists with your own content, verikt uses sentinel markers to update only its section:

```markdown
## Our coding standards
...your existing content stays here...

<!-- verikt:start -->
# verikt — layered Architecture
...generated content...
<!-- verikt:end -->

## Other team guidelines
...also stays here...
```

Re-running `verikt guide --target copilot` updates only the content between `<!-- verikt:start -->` and `<!-- verikt:end -->`. Everything outside is untouched.

<Aside type="tip">
Commit `.github/copilot-instructions.md` to the repository. It's in `.github/` already — the directory every engineer expects for repository-level configuration. No extra setup required for anyone joining the project.
</Aside>

## Keeping the guide current

The guide reflects the current state of `verikt.yaml`. Re-run it after adding capabilities:

```bash
verikt guide --target copilot
```

If you want to update all targets at once:

```bash
verikt guide
```

Running without `--target` regenerates the files of every agent the project already uses — `.claude/rules/`, `.cursor/rules/verikt.mdc`, `.github/copilot-instructions.md`, `.windsurfrules`, `AGENTS.md` — in a single pass, along with the on-demand references in `.verikt/references/`. When the project carries none of them yet, it writes all of them.

## What this changes

In [EXP-09](/experiments/exp-09/), the guide changed not just what the agent built but what it recommended. Without the guide: vague suggestions to "consider adding retries." With the guide: an exact `verikt add retry circuit-breaker idempotency` command, because the guide's interaction warnings made the dependency chain explicit.

That experiment ran one model, claude-sonnet-4-6, against the single-file guide verikt generated before 0.3.0. Copilot was not measured, and neither was the current two-tier guide, so treat the result as evidence about the content, not a measured effect in Copilot.
