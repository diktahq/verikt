Cursor loads project rules from `.cursor/rules/` — a rule marked `alwaysApply: true` goes into every request. Most teams put coding style preferences there — linting rules, naming conventions. Almost none put architecture rules. The mechanism exists, but the architectural context that would make the agent most useful isn't in it.

`verikt guide --target cursor` writes `.cursor/rules/verikt.mdc`, an always-applied rule with your layer boundaries, dependency direction, installed capabilities, and critical warnings — derived from `verikt.yaml`. Cursor gets your architecture on every request, not just when you remember to explain it.

## Quick start

Install verikt, then generate the rules file:

```bash
brew install diktahq/tap/verikt
verikt guide --target cursor
```

The generated rule lands in `.cursor/rules/verikt.mdc`, alongside on-demand references in `.verikt/references/` that the rule points the agent to when a task needs more detail. Cursor picks the rule up automatically on the next session.

## What gets generated

Every target gets the same compact rules; only the file and its frontmatter differ. An excerpt for a hexagonal service, with the agent instructions and warnings left out:

```
## Architecture: hexagonal

Hexagonal (ports & adapters). Business logic in domain + service layers, isolated by ports (interfaces) and adapters (implementations).

## Layer Rules

- **domain**: depends on nothing (innermost)
- **ports**: depends on domain
- **service**: depends on domain, ports
- **adapters**: depends on ports, domain, platform
- **platform** (optional: may be absent): depends on domain
- **app**: depends on domain, ports, service, adapters, platform

## References (read on demand)

- Read `.verikt/references/architecture.md` before adding a package or file, or an import that crosses a layer.
- Read `.verikt/references/capabilities.md` before adding or wiring a capability (transport, data, resilience, security).
- Read `.verikt/references/review.md` before you finish a change, and when reviewing code.
```

The always-loaded rule stays within 30 instructions and 1,500 tokens; the directory globs, forbidden imports, capability catalog and review checklist live in the references.

The agent now knows your layer names, the direction dependencies flow, and the explicit rules — without you restating them in each prompt.

## Your own rules stay yours

`.cursor/rules/verikt.mdc` belongs to verikt and is rewritten on every run. Keep your own rules in other files under `.cursor/rules/`; verikt doesn't touch them.

## Migrating from `.cursorrules`

Earlier versions of verikt wrote a sentinel-delimited section into `.cursorrules`, Cursor's legacy single-file format. Cursor deprecated that file, so verikt now moves its section out the next time you run `verikt guide`. Your own content in `.cursorrules` is kept; the file is deleted only when verikt's section was all it held. A notice on stderr says which happened. If the markers in `.cursorrules` are malformed, verikt leaves the file untouched and tells you to remove its old section by hand rather than guess.

<Aside type="tip">
Commit `.cursor/rules/verikt.mdc` and `.verikt/references/` to the repository. Every engineer working in Cursor gets the architecture context automatically — no setup step, no documentation to read first.
</Aside>

## Keeping the guide current

The guide is generated from `verikt.yaml`. After adding a capability with `verikt add`, re-run the guide to keep the rules current:

```bash
verikt guide --target cursor
```

Stale architecture rules are worse than no rules — the agent follows the outdated context confidently.

## What this changes

In [EXP-01](/experiments/exp-01/), the same task ran without any guide and with verikt context loaded. Without: the agent defaulted to flat structure, 0% hexagonal compliance. With: 100% compliance across all three runs. The variable was the loaded context.

The same effect applies in Cursor. The project rule is just the delivery mechanism.
